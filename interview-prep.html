Explain Data-Berge OS with confidence.

A fast briefing for discussing the product, architecture, AI design, security decisions, trade-offs, and your next steps.

Your 90-second answer

Data-Berge OS is a multi-tenant analytics workspace. A user can upload CSV or Excel files, connect to public datasets, or register a remote PostgreSQL/Supabase table. The backend profiles the data—types, missingness, duplicates, statistics, correlations, and quality flags—and stores that profile for reuse.

Users can ask questions through chat, create charts, and generate executive reports. The AI architecture uses a manager agent to route requests to a Data Analyst, Data Engineer, or Report Agent. The model handles intent and planning, while deterministic services perform profiling and restricted SQL execution.

For remote databases, the system uses federation instead of copying the whole database. Credentials are encrypted and queries are bounded, read-only, and limited to the registered table. The stack is React and TypeScript, FastAPI and Python, PostgreSQL, Redis, S3-compatible storage, and background workers.

Production boundary

PostgreSQL stores metadata and durable job state. S3-compatible storage owns files. Redis/RQ handles queues. Stateless API replicas and independent workers can scale separately.

Important distinction

Materialized: CSV, Excel, and OpenDOSM are downloaded/profiled locally.

Federated: PostgreSQL/Supabase data stays remote; Data-Berge stores connection metadata and queries a bounded logical dataset.

Key sentence: “The LLM is not the source of truth. It chooses the action and specialist; deterministic tools produce the evidence.”

  • Data Analyst: facts, calculations, profiling, trends, charts.
  • Data Engineer: data quality, typing, joins, schema readiness.
  • Report Agent: report planning, revision, approval, and generation.

Security talking points

  • HttpOnly JWT session cookies plus a separate CSRF token.
  • Bcrypt password hashing.
  • Every project and dataset lookup validates user ownership.
  • Connector secrets are encrypted and never returned to the browser.
  • Federated queries are read-only, timed out, and result-limited.
  • Private hosts, system schemas, multiple statements, joins, and dangerous functions are rejected.

Honest limitations

  • Model-led routing can still misclassify unusual requests.
  • Regex SQL validation should eventually be complemented by an SQL parser/AST approach.
  • Federated profiles are based on a bounded sample and estimated row count.
  • Fine-grained RBAC, append-only audit events, retention, and disaster recovery are future enterprise work.

Improvement answer: “I would add an evaluation dataset for routing and answer correctness, measure latency/cost, and expand auditability and lineage.”

Likely questions

Why use multiple agents?

To separate responsibilities and reduce uncontrolled behavior. Each specialist has a narrower role, tools, and validation path.

How do you reduce hallucinations?

Dataset facts are delegated to tools. Counts come from profiles or SQL results, responses include evidence, and simple shape questions can use deterministic code without an LLM.

What happens when the model fails?

Structured decisions are validated. Invalid or unavailable manager output falls back to deterministic routing, and greetings stay out of analytical agents.

How would you scale it?

Keep APIs stateless, move long work to workers, use PostgreSQL for metadata, S3 for files, Redis/RQ for queues, and scale API and worker replicas independently.

What would you improve first?

Build a production evaluation set, add richer observability for quality/latency/cost, strengthen SQL validation, and add audit logs and lineage.
